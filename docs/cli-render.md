# `context-engine render`

`context-engine render` runs the existing governed construction and rendering
pipeline from one explicit local JSON input document. It is a local
application boundary: it neither observes Sources, extracts semantic content,
infers applicability or roles, nor delivers rendered content to a Consumer.

## Invocation

```bash
context-engine render \
  --input ./governed-render-input.json \
  --output ./rendered-context.txt
```

The output path must name a file that does not yet exist. The command writes a
complete UTF-8 rendering atomically, never overwrites an existing file, and
prints a JSON summary containing the selected-item count, sufficiency,
coherence, and rendering status. A nonzero exit leaves no new output file.

## Input document

The document is JSON with `"version": 1`. Relative Bootstrap and Project
configuration references are resolved relative to the input document. It is a
strict adapter for `GovernedRenderInputs`; every listed field is required and
unknown fields fail validation.

| Section | Required governed input |
| --- | --- |
| `bootstrap_reference`, `project_configuration_reference`, `operator_authorized` | Explicit Bootstrap establishment inputs. `operator_authorized` is never defaulted. |
| `request` | Existing `ContextRequest` fields: identities, requester, Consumer, intent, scope, and constraints. |
| `universe` | Existing ASU request reference, registered Sources, adequacy, and establishment basis. |
| `evidence` | Existing `DiscoveryEvidence`: a represented-information object with full provenance plus its registered Source, discovery evidence, and governed metadata. |
| `query_terms` | Explicit discovery terms. |
| `applicability` | One explicit `ApplicabilityInputs`/`EnforcementInputs` entry for every represented-information identity in `evidence`. |
| `role_inputs` | One explicit `RoleInputs` entry for every represented-information identity in `evidence`. Missing entries fail closed rather than becoming an implicit exclusion. |
| `selection_basis`, `sufficiency_deficiencies`, `material_conflict`, `material_uncertainty`, `bounded_task_safe` | Existing selection and sufficiency inputs. |
| `package_identity`, `record_identity`, `termination_basis`, `coherence_inputs`, `construction_qualifications` | Existing package-construction inputs. |
| `contract` | Existing `ConsumerContract`: kind, Consumer identity, disclosure authorization, and optional character capacity. |
| `scope_inputs`, `expansions` | Existing discovery scope/expansion inputs. |

Every semantic identity is an object such as `{"kind":"request","value":"request-1"}`. A classification is an object with `name` and `provenance` (which may be `null`). Every optional value must be represented explicitly as either its valid value or `null`; boolean authorization fields must be JSON booleans. The CLI validates enum values, identity coverage, duplicate applicability/role keys, Source registration, Bootstrap/project matching, and the existing runtime authorization gates.

## Minimal workflow

1. Establish and validate the Bootstrap and Project configuration TOML files.
2. Prepare an explicit v1 JSON document from already governed evidence. This
   is an input adapter, not a replacement for semantic ingestion or lifecycle
   resolution.
3. Supply all task-relative applicability and counterfactual role inputs.
4. Set authorization values only when separately established for the run.
5. Invoke `context-engine render` with a new output path.

For example, a successful command prints a summary shaped like:

```json
{"coherence":"coherent","output":"./rendered-context.txt","rendering_status":"rendered","selected_context_items":1,"status":"rendered","sufficiency":"sufficient"}
```

If Bootstrap authorization, requester/disclosure authorization, input
validation, applicability, role coverage, construction, or rendering fails,
the command returns a nonzero status and does not create the selected output.

## Day Trading System reference

The frozen Day Trading System Stage 1 rendering remains historical Phase 4
evidence and is not overwritten or regenerated by this command. Its committed
candidate inputs are governance records rather than a complete v1 CLI input
document. For this command's local acceptance, a temporary explicit v1 input
recovered from the preserved, hash-validated Stage 1 inputs reproduced the
frozen rendering byte-for-byte: 60,405 bytes and SHA-256
`63adec37b9ba7199dd9731e4ba3726840fcf4ed97d7224234dfe6d74558769a1`.
The CLI can render that scenario when an operator supplies an exact, separately
governed v1 document containing its already-resolved semantic evidence and
explicit applicability/role decisions; it does not convert Markdown records or
infer the runtime object graph.
