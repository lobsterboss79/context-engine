## Complete pre-frozen vertical sequence

1. Create the deterministic Alpha source database containing Project/Source/observation/artifact/transformation/representation/Provenance/construction/audit history and explicitly historical evidence with `currentness=unknown` and no Authority basis.
2. Create a local manual Alpha backup at an explicit new destination using the explicit purpose `Phase 4 WS4 Lane C controlled local recovery validation` and the bounded fixture-only retention basis `retain only in this VE-P4-4C-001 record; no scheduler, duration, or deletion policy selected`. Validate it through `validate_backup`, record metadata and SHA-256 identities.
3. Prepare a distinct, valid Beta target. Freeze the controlled failure boundary by replacing only the process-local `sqlite_state.os.replace` reference with a function that raises `OSError("controlled replace interruption")`. Attempt restore; retain the failed-replace predecessor state, failure message/classification, and target SHA-256. This scenario-expected state is `RECOVERY REQUIRED`; it is not a validation-control FAIL.
4. Remove only that process-local injection. Re-validate the unchanged backup, stage and restore it under the same local/manual operator-authorization input. Record restore qualification, source/backup/restored identities, SQLite integrity, raw database hashes, semantic projections, and audit authorization denial.
5. Independently classify the successor against this ER. The predecessor remains immutable historical evidence; successor success cannot change its expected failure classification.

No alternate retry, cleanup, fixture alteration, source/test alteration, or recovery path is authorized. Any unexpected behavior is STOP AND PRESERVE.

## Predetermined expectation and acceptance criteria

The scenario expects a controlled failed replacement followed by an independently successful local/manual restore. The validation control is **PASS** only if all are true:

1. Backup creation requires the explicit destination, purpose, and bounded fixture-only retention basis; its metadata has one secret-safe row, schema version 5, and passes integrity/compatibility validation.
2. The controlled failed replacement raises `RestoreError`, leaves the valid Beta target byte-identical and semantically intact, leaves no staging file, and preserves a distinct predecessor evidence projection. It does not appear as a successful restore.
3. The successor restore is authorized at the modeled application seam, validates the unchanged backup before and after staging, replaces the target only after staging validation, and leaves no staging file.
4. The restored Alpha state semantically retains Project association, Source registration, observation, artifact/transformation/representation lineage (Provenance), governance/history-bearing evidence, construction record, and authorized audit row. Source and restored semantic projections must match except for the permitted new `recovery_qualification` row; the backup and restored files must each pass integrity validation and have recorded hashes.
5. Beta is absent after successful replacement; all Alpha lookups remain Project-scoped. An unauthorized Alpha audit read is denied, and no Beta audit/record is exposed through Alpha-scoped lookups.
6. Recovery qualification names the backup identity and expressly retains historical-only status. The restored evidence remains `currentness="unknown"` with no Authority basis. No recovery, backup metadata, or restored schema field establishes Authority, Governance State, present authorization, currentness, receipt, use, or sufficiency; construction remains explicitly `insufficient`/`coherent_with_qualification`.
7. Recovery preservation is explainable: predecessor hashes and failure facts are retained separately, no predecessor artifact is rewritten, and only independently classified successor evidence claims the successful restore. Diagnostics are recorded as diagnostics, not durable audit or recovery evidence.

## Negative criteria / validation-control FAIL conditions

The control is **FAIL** if the backup/restore creates or needs scheduling, remote storage, retention-duration/deletion policy, RPO/RTO, HA, service/daemon, container, cloud infrastructure, or another environment; touches non-disposable data; modifies source/tests/shared material; loses or changes Alpha durable evidence; leaks/crosses Projects; replaces Beta during the injected failure; leaves the recovery qualification absent or semantically elevating; manufactures any prohibited present status/sufficiency; treats diagnostic text as durable audit/recovery proof; or lacks reproducible raw evidence needed to evaluate a criterion.

Missing/contradictory evidence that prevents this evaluation is **INDETERMINATE**, never PASS. An unexpected failure or ambiguity is STOP AND PRESERVE under WS1/H3; this ER is not revised post-execution.
