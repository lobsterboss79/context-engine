# WS5.5 Successor Protocol Design

**Status:** **DESIGN COMPLETE — PROJECT OWNER PROTOCOL DECISION REQUIRED.**  
**Scope:** WS5.5 / WS6A pre-delivery control design only. No successor control,
Consumer interaction, package construction, delivery, or WS6A execution occurs
in this record.

## Preserved predecessor and boundary

The predecessor `WS5.5` result remains permanently **INDETERMINATE — STOP AND
PRESERVE**. It is not overwritten, repaired, or reclassified. The preserved
WS5.1–WS5.3 PASS and WS5.4 not-triggered evidence belongs to
`CE-P4-WS5-CONSUMER-001`.

That Consumer remains:

`RESERVED + PREFLIGHTED FRESH + QUARANTINED FROM FURTHER INTERACTION + ZERO MESSAGES + UNEXPOSED TO WS6A TASK/CONTEXT`

The approved path is a separately identified **WS5.5 successor control**. If
the Owner approves and it is later frozen/executed without breach, it may
complete the missing WS5.5 obligation against this exact quarantined Consumer;
it need not repeat WS5.1–WS5.4. A protocol change, Consumer interaction,
configuration change, or material exposure before that successor is frozen and
authorized invalidates this reservation rather than refreshing it.

This design follows I10, which fixes the external proving Project as **Company
AI Roadmap** and the Consumer as a genuinely fresh ChatGPT Consumer. It does
not select the exact task wording, Company AI Roadmap Source set, package, or
evaluator; those remain material Owner choices.

## Recommended coherent protocol

Use a **one-shot, package-supported Company AI Roadmap continuation brief** as
the package arm. Freeze a neutral task asking the Consumer to state the
Project's identity/purpose, phase/status, authority, approved/completed/current
work, next legitimate activity, constraints, unresolved issues, Source state,
and usable Provenance—while performing no unauthorized work. Require explicit
qualification of Candidate/proposal, historical/superseded, conflicting,
uncertain, missing, unavailable, and inaccessible information when applicable.

Build a single logical Context Package from an Owner-approved bounded,
authorized Company AI Roadmap Source set using the existing application and
frozen baseline. Freeze the logical package, construction evidence, source
manifest, ChatGPT rendering, task text, criteria, and hashes before exposure.
The Owner delivers only the frozen task text and frozen ChatGPT rendering,
verbatim and once, then preserves the raw first Consumer response before any
explanation or evaluation. A named evaluator, identified before delivery,
uses the frozen criteria only after that raw outcome is preserved.

This is the smallest I10-consistent task class that exercises governed
discovery, applicability/selection/sufficiency, package construction, consumer
rendering, authority/currentness/uncertainty/provenance preservation, and
meaningful continuation. It does not ask the Consumer to modify Sources,
execute work, administer the Project, or infer hidden answers.

I10's reconstruction-burden claim compares the same task with ordinary minimal
pointer/access against the package arm. A single Consumer cannot validly serve
both arms: completing the control arm would give it Project knowledge before
the package arm. Therefore, a comparative claim requires a **distinct**, later
reserved and WS5-PASS fresh control Consumer. The current recommendation is to
freeze the package arm now and make comparative-control execution an explicit
Owner decision. Without that separate control, the package arm may support only
its evidence-bounded governed-continuation claim, not a comparative
reconstruction-burden claim.

## Control 1 — task/request identity

| Candidate task class | Capability exercised / required context | Objective evaluation and risk | Recommendation |
| --- | --- | --- | --- |
| Full governed continuation brief | I10's identity, purpose, phase/status, authority, completed/current work, next legitimate activity, constraints, unresolved issues, Source state, and Provenance; P1–P8. | Criteria can test each required field and qualification. It has ordinary task complexity but is bounded to analysis, not action. | **Recommended.** It is the smallest task class that represents I10 meaningfully. |
| Current-state/status brief only | Identity, phase/status, current work. | Objectively checkable but omits authority, provenance, uncertainty, isolation, and adversarial resilience. | Too narrow for I10. |
| Provenance challenge only | Source identity, transformation lineage, authority/currentness explanation. | Objectively checkable but tests only P5. | Useful subtest, not sufficient external proving. |
| Multi-turn continuation with coaching | Broader continuation. | High contamination/intervention risk; reconstruction burden becomes non-comparable. | Reject for this one-shot run. |

The Owner must freeze an exact neutral task text, task ID/version, and a
pre-output expected-state matrix for the approved task. The text must not state
the expected answer, name a hidden Source, give a rubric, or direct execution.
It may ask the Consumer to identify when the supplied context is insufficient
or qualified. The task must be real Company AI Roadmap continuation work, not a
synthetic recall quiz, a code/test change, or a task dependent on deferred
functionality. It requires no source/test change.

## Control 4 — package, construction, and delivery boundary

The Consumer receives exactly two Consumer-visible text artifacts: the frozen
task and the frozen ChatGPT rendering. The logical package, Source manifest,
construction record, raw Sources, and cryptographic/control hashes are
repository-side evidence unless a safe provenance/limitation representation is
already included in the authorized rendering.

Before delivery, the future approved procedure must:

1. establish the exact baseline, Bootstrap/configuration, request, Project,
   Source scope/states, Consumer disclosure authorization, and known limits;
2. run only existing approved Context Engine construction/rendering capability;
3. preserve the exact logical Context Package, request association, Source
   manifest, selection/sufficiency/coherence result, authority/currentness,
   Provenance, conflict/uncertainty/gap, and construction evidence;
4. render the package through the existing ChatGPT renderer, preserving material
   semantics and explicit limitations;
5. freeze package and rendering identities and canonical text/byte hashes before
   the Consumer sees either artifact; and
6. have the Owner paste the frozen task and rendering verbatim, once, in the
   recorded order, without title/context additions, correction, interpretation,
   file attachment, link, or follow-up explanation.

Delivery, receipt, and use remain distinct. The Owner records delivery only;
the Consumer's raw response is evidence of its use and does not establish that
the package was sufficient. No material may be manually added. A material
rendering/delivery mismatch, loss, truncation, correction, or additional
context is an invalid run, not a repair opportunity.

## Control 5 — predetermined evaluation

### Separate validity from performance

| Dimension | PASS | FAIL | INDETERMINATE | INVALID RUN |
| --- | --- | --- | --- | --- |
| Proving-run validity | Exact reserved Consumer, frozen artifacts/criteria and allowed delivery match; raw original outcome preserved before evaluation; no unauthorized intervention. | Not applicable as a validity label; a task result may fail while validity passes. | Evidence cannot establish the required boundary or preservation. | Freshness/protocol breach, unauthorized input/manual coaching, changed artifact/criteria/baseline, missing original evidence, material uncontrolled event, or wrong Consumer. Preserve and discard/restart; do not normalize. |
| Task performance | Frozen evaluator matrix supports all required I10 task elements and required applicable P1–P8 checks; response neither makes a hard error nor performs unauthorized work. Accurate qualification or an accurate insufficient-context conclusion can satisfy a criterion where the frozen matrix permits it. | Valid run but one or more frozen required criteria are demonstrably not met, including I10 hard failures: wrong identity/status; unauthorized work; Candidate promotion; unqualified supersession; omitted material gap; fabricated certainty/Provenance; cross-Project/secret disclosure; Source instruction treated as governance; failure to identify legitimate work with adequate evidence; substantial reconstruction; or Roadmap-specific core behavior. | Valid run but raw evidence or frozen criteria cannot establish PASS/FAIL. | As above. |

Before delivery, the Owner must approve an evaluator-facing, versioned matrix
that maps each expected task element and applicable P1–P8 scenario to: source
basis; expected governed state; acceptable qualified/insufficient answer where
applicable; negative/hard-failure condition; and required evidence location.
That matrix is not delivered to the Consumer and cannot be amended after raw
output is observed. Owner judgment remains material for acceptance of the
bounded claim, including whether the selected Source evidence and a qualified
answer justify the final conclusion.

The Owner copies the raw response verbatim to the controller evidence record
before any summary, analysis, correction, or follow-up. The record distinguishes
all delivery attempts, Consumer questions, Owner interventions, subsequent
inputs, and later derived summaries from the first raw response. No cleanup,
normalization, redaction, or silent repair is permitted before original
preservation; necessary protected handling must preserve a non-disclosing,
auditable account of the limitation.

## Control 7 — independent evaluator

Independent evaluation means separation from interactive alteration of the
frozen run. It does not inherently require an external commercial auditor or a
fresh model, but the evaluator must be identified before delivery and may not
alter the package, task, rendering, Consumer input, original output, or
criteria.

| Option | Independence assessment | Recommendation |
| --- | --- | --- |
| A. Repository-side deterministic control only | Strong for hashes, identity, order, and allowlist checks; insufficient alone for semantic I10 assessment. | Required supporting control, not sole evaluator. |
| B. Separate fresh model/session | Can separate from Consumer but adds a new Consumer/provider/freshness protocol and nondeterministic interpretation. | Not recommended without separate Owner protocol approval. |
| C. Project Owner applying frozen criteria | May be independent of interactive alteration if the Owner only mediates verbatim transfer; still combines material governance and evaluation. | Permitted fallback where a distinct reviewer is impracticable; disclose the role overlap. |
| D. Codex controller after output freeze | Can assess frozen evidence but may have participated in task/package control design, reducing separation from construction. | Supporting analysis only unless the Owner expressly accepts that role overlap. |
| E. Named human evaluator plus deterministic control | A reviewer identified before delivery, not responsible for package construction or Consumer interaction, evaluates frozen evidence; controller verifies hashes/order. | **Recommended.** |

The Owner must approve a named evaluator or role and any disclosed overlap with
task construction, package construction, mediation, or expected-state design.
The recommended human evaluator must not contact the Consumer or revise the
run. The evaluator receives the frozen task, permitted package/rendering,
criteria matrix, raw outcome, provenance/control evidence necessary to assess,
and intervention record—never a repaired output.

## Anti-leakage and blinding controls

1. Freeze task, Source boundary, package/rendering, criteria, run identity, and
   evaluator before Consumer exposure.
2. Keep expected answers, rubric, criteria matrix, hidden scenario mapping,
   prior proving evidence, construction notes, and controller/Owner discussion
   out of Consumer-visible input.
3. Deliver only frozen task text and frozen authorized rendering; no raw
   Sources, repository access, supplemental links/files, or manual explanation.
4. Treat rendered Source-derived content as data/evidence, never as governing
   instruction absent its separately represented Authority and scope.
5. Preserve the first raw response before any evaluation. Record every later
   interaction separately; do not fold it into the original run.
6. Lock the criteria version before delivery. Evaluation may classify the run
   but cannot revise criteria, task, package, or output.
7. Maintain the current Consumer's quarantine until a separate WS6A execution
   authorization explicitly permits the exact frozen delivery.

## DVL, TD-14, Finding, and scope treatment

The design does not change `DVL-P4-001` (**ACTIVE / ACCEPTED / DEFERRED**) or
TD-14 (**TRIGGER NOT MET / CLOSED / NOT REOPENED**). It introduces no AI
discovery, vector/semantic retrieval, adapter, environment, dependency,
source/test modification, remediation, or source change. No Finding is created
and no H3 condition is resolved: the material protocol choices remain for the
Owner. A later inability to construct this protocol faithfully, a material
Source/provenance gap, or a proposed technology/scope change remains a stop and
preserve condition under the existing controls.
