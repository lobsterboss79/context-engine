## Governing compatibility determination

### What approved records require

The approved proving claim is not provider-neutral with respect to its Project:

1. Phase 0 §14 success criterion 9 requires a fresh ChatGPT session to use an
   **AI Roadmap** package for meaningful continuation with substantially less
   manual reconstruction.
2. Phase 0 §15 identifies **Company AI Roadmap** as the *first external proving
   ground*; Context Engine is the separate dogfooding case.
3. Phase 1 Item 53 requires the Company AI Roadmap proving ground to exercise
   meaningful continuation, state distinctions, isolation, provenance, and
   comparison with manual reconstruction.
4. Phase 2 I10 states: “The proving Project is Company AI Roadmap,” and fixes
   a genuinely fresh ChatGPT Consumer plus the I10 continuation and P1–P8
   scenarios.
5. Phase 4 WS6A's stated purpose is useful context for a **real project other
   than Context Engine**.

Accordingly, a purpose-built fictional corpus is **not currently a permitted
substitute for the approved WS6A Company AI Roadmap exercise**. It would change
the named proving Project and remove the approved real-project condition. This
is a material proving-protocol/scope decision, not an ordinary implementation
choice that Codex may make.

### Instrumentation versus validation fixture

The architecture permits controlled Sources, deterministic fixtures, known
inputs, and predetermined expected results for **WS2 validation**. Those
fixtures are expressly non-production control data; they validate pipeline
behavior under controlled conditions. The execution contract's reference to
run-specific “control, fixture, and evidence preservation” does not turn a
synthetic fixture into the real external Project required by I10/WS6A.

A purpose-built, fictional, self-contained corpus could be architecture-
compatible as either:

- controlled validation data/instrumentation for a bounded validation exercise;
  or
- a candidate new proving protocol after an explicit Owner-approved amendment
  defines what narrower or different claim it could support.

It cannot support the existing Company AI Roadmap proving claim, its
real-project conclusion, or its reconstruction-burden comparison merely by
being designed to contain the same semantic patterns. The prior statement that
synthetic fixtures were unsuitable was therefore specific to the proposed I10
external-proving substitution, not a claim that fixtures are fundamentally
forbidden everywhere.

## Conditional corpus design — not authorized for creation or WS6A substitution

If the Owner later approves a separately bounded fictional-corpus protocol,
the smallest coherent fictional Project should be a self-contained,
non-sensitive Git/Markdown Project with one continuation task and no company,
client, personal, proprietary, copied external, credential, secret, or
production content. Its potential purpose would be to demonstrate a narrower
controlled-consumer context claim—not the current I10/WS6A claim unless the
governing records are expressly amended.

### Conditional task and comparison design

The conditional task class would be a neutral one-shot continuation brief:
identify current Project state; governing/current decisions; superseded
information that does not control; applicable limitations and uncertainty;
unresolved or insufficient areas; usable provenance; and the next authorized
work boundary, without performing work. The task must be frozen before either
Consumer sees it and must not contain answer text, an evaluation rubric, or
proving instructions.

The package arm would receive only frozen task plus authorized Context Engine
rendering. A distinct fresh control Consumer would receive the same task plus a
frozen ordinary minimal pointer/access baseline. Neither receives expected
answers, rubric, package-arm output, coaching, or follow-up. The exact control
baseline remains a material Owner decision even in a fictional protocol.

### Conditional expected-state and anti-overfitting design

Before any Consumer exposure, an evaluator-only manifest would classify each
expected fact as Required, Permitted, Prohibited, or
Unresolved/Insufficient and trace it to the fictional Bootstrap/Source corpus.
It would assess current/guiding state, non-use of superseded material,
limitations/uncertainty, authority/provenance, instruction/data separation,
omission/hallucination, and comparative reconstruction burden. The Consumer
would not receive it.

Creating corpus and expected-state records in one workflow is not inherently
architecturally circular when both are frozen before package construction and
the package builder cannot read evaluator-only answer material. It does,
however, create controlled-instrumentation evidence rather than external-
Project proving under current I10. Required safeguards would be:

1. freeze corpus and its Source/version manifest before package construction;
2. freeze expected-state manifest before Consumer exposure;
3. keep expected-state and rubric hidden from both Consumers;
4. deny package construction access to evaluator-only expected-answer material;
5. preserve package/rendering/task/criteria/source hashes and ordered events;
6. prohibit post-output criteria or corpus changes; and
7. separately preserve raw Consumer output before evaluation.

as `docs/phase-4/proving/corpus/` would make its non-production, proving-only
status explicit and keep it distinct from application source and ordinary WS2
validation fixtures. Whether Markdown documents in that namespace are directly

Markdown Project boundary outside `docs/`, must be established before creation;
this analysis selects neither location nor representation.

Creation is **not authorized by this analysis**. It requires a separate Owner
decision that either:

1. authorizes a bounded controlled-instrumentation exercise outside WS6A with
   its own claim, protocol, expected-result controls, and evidence treatment;
   or
2. amends the I10/WS6A proving protocol and its claim/acceptance basis to
   replace the named real Company AI Roadmap exercise with a fictional corpus.

The second path is a material scope/governance amendment and must assess
effects on Phase 0 success criterion 9, Phase 0 §15, Phase 1 Item 53, Phase 2
I10, the Phase 4 checklist WS6A purpose, previous protocol records, expected
criteria, and any claim about external-project capability or reconstruction
burden.
