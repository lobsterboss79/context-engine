# Expected-Result Register Template

**Template status:** Pre-execution artifact. Establish and approve as applicable before associated execution. An observed result never silently changes an expectation.

| Field | Record value |
| --- | --- |
| Expected Result ID | `ER-[stable ID]` |
| Version | `v[n]` |
| Status | `[draft / governed for authorized execution / superseded]` |
| Governing requirement/design reference | `[approved reference(s)]` |
| Validation/checklist/protocol item | `[future item]` |
| Controlled input/fixture/Source identity | `[identity and provenance]` |
| Bootstrap/configuration/environment basis | `[future identity]` |
| Governed expectation | `[predetermined expected behavior]` |
| Acceptance criteria | `[measurable/evaluable criteria]` |
| Negative/failure criteria | `[defined failure conditions]` |
| Known limitations/qualifications | `[applicable limitations]` |
| Reviewer basis | `[approved semantic/design basis used to assess]` |
| Governing/approving authority where applicable | `[authority, date, decision reference]` |
| Affected evidence | `[future Evidence IDs]` |
| Revision reason and lineage | `[prior version, reason, approval; never overwrite prior version]` |

Use **PASS**, **FAIL**, or **INDETERMINATE** only in linked future evidence records. If the governing basis is genuinely ambiguous, preserve the issue and escalate under H3; do not invent an expectation.
