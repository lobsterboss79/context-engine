# v0.1 Baseline and Requirements-to-Phase-0 Traceability

## v0.1 required-capabilities baseline (Item 51)

v0.1 is a proof of capability, not maximum maturity. It must demonstrate these approved capability areas:

1. Register and recognize a Project.
2. Access local Git repositories, Markdown, and structured metadata where necessary.
3. Identify Artifacts and sufficiently granular relevant information.
4. Preserve Provenance.
5. Represent Authority and Governance State.
6. Handle currentness and supersession.
7. Preserve Project isolation.
8. Accept task-oriented Context Requests.
9. Perform task-specific Context Selection.
10. Represent Conflict, Uncertainty, and material gaps.
11. Produce a logical Context Package.
12. Render for Human, ChatGPT, and Codex Consumers.
13. Explain material selection and Provenance.
14. Enforce baseline security behavior.
15. Produce an auditable package record.
16. Demonstrate Source extensibility.
17. Pass the Company AI Roadmap external proving-ground test.
18. Pass Context Engine dogfooding.
19. Demonstrate a non-circular governed Governance Bootstrap sufficient for the proving Projects.

These capabilities trace to approved requirements and Phase 0. They are proved sufficiently against the proving grounds; unnecessary capabilities remain outside v0.1 unless explicitly approved.

### Approved initial Source-support boundary (Item 56 resolution)

For v0.1, local Git repository support is more than filesystem access to files located in a Git working tree. The Context Engine must be capable of recognizing a governed local Git repository as a Source and preserving and using material Git-native state when relevant to the Context Request: repository identity; applicable revision/commit state; current branch or equivalent repository state; relevant working-tree state where that distinction materially affects context; and relevant historical/version information required for provenance, currentness, supersession, or task correctness. Observed local Git state must remain distinguishable from independently verified lineage, remote/shared, governing, complete, or current state; a commit, branch, remote name, or clean working tree cannot independently establish those stronger claims. Material unsupported, unavailable, incomplete, or indeterminate Git-native properties participate in uncertainty and sufficiency. Git history need not be exhaustively retrieved or processed when it does not materially contribute to the task.

Markdown support means the engine can identify and retrieve governed Markdown Artifacts and preserve sufficient Source/Artifact provenance for correct interpretation. Structured metadata is required only where information necessary to satisfy an approved requirement cannot be represented or reliably established through supported Source/Artifact information alone. Phase 1 selects no structured-metadata representation, storage mechanism, schema, or technology.

A Source type is demonstrated as supported when v0.1 can: (1) recognize the governed Source; (2) operate within approved scope; (3) identify supported information/state; (4) preserve material native provenance/state available from that Source; (5) represent unsupported/unavailable properties honestly; and (6) use materially relevant Source-native information in Context Selection and package construction when required by the task. This does not authorize a full Git analytics/history system or another Source integration.

### Approved v0.1 acceptance interpretations (Item 56 resolution)

These interpretations govern Phase 1 acceptance meaning without selecting test procedures, architecture, technology, or numerical thresholds.

- **Sufficient Context:** a designated acceptance exercise demonstrates that the intended Consumer can perform the defined task correctly without additional material project-state reconstruction from the Project Owner, and no known omitted, unavailable, conflicting, unauthorized, stale, uncertain, materially incoherent, or materially undelivered information would reasonably invalidate or materially alter that performance. The determination has an explainable, inspectable evidence/inspection boundary, including a reasonably adequate Applicable Source Universe; absence of discovered deficiencies alone is insufficient. **Conditionally Sufficient** means the Consumer can perform correctly within explicitly stated material qualifications. **Insufficient** means one or more known material deficiencies prevent trustworthy performance.
- **Usable Provenance:** for each material governing or task-critical Context Item selected for an acceptance exercise, an authorized reviewer can trace it to enough originating Source/Artifact/version or observed state and material transformation lineage to determine origin and why represented Authority, currentness, and status are justified. This does not require a citation on every sentence.
- **Meaningful Continuation:** using the generated Context Package and ordinary task instructions, a fresh Consumer can correctly identify governed current state; respect authorization and phase boundaries; distinguish approved/current information from Candidates, history, Conflict, and Uncertainty; identify the next legitimate activity; and perform substantive next-step work, without the Project Owner manually reconstructing material prior project state.
- **Substantially Less Manual Reconstruction:** the Project Owner need not provide a separate material project-state briefing beyond the task instruction and generated Context Package before a fresh Consumer can meaningfully continue. Normal Project Owner participation in subsequent decisions is not manual reconstruction; supplying missing prior project state is.
- **Credible Additional-Source-Adapter Path:** an architecture review can identify how a materially different Source type could be introduced through the approved Source boundary without changing the governed meaning of Project, Source, Artifact, Claim, Authority, Provenance, Context Request, Context Item, or Context Package solely because its native technology differs. It does not require implementing a deferred adapter.
- **Substantial Reproducibility:** an authorized reviewer can determine the material request state, Consumer, preserved available Source states/versions, selected context, material qualifications, sufficiency determination, and Consumer rendering sufficiently to explain what was supplied and why, even when exact byte-for-byte regeneration is impossible.

Acceptance criteria must be observable and repeatable enough for a reasonable reviewer to understand a pass or failure; no arbitrary numerical threshold is required unless later evidence establishes one. Qualitative criteria may be satisfied through defined proving exercises and Project Owner review. Evidence evaluates behavior rather than merely documentation or components, may not depend on undocumented Consumer knowledge, and must account for material qualifications, failures, Conflict, Uncertainty, Applicable Source Universe/evidence boundary, construction-state coherence, and receipt rather than ignore them to obtain a pass. For proving-ground acceptance, preserve as applicable the task/instructions; Context Package or durable reference; Consumer/rendering; material Source/inspection boundary; material post-package manual intervention; evaluated Consumer result; material failures/corrections; acceptance criteria; and Project Owner disposition/rationale. Record material manual reconstruction or repair after generation rather than silently treating it as package success. A proving task must materially exercise the claimed capability; acceptance need not use an independent certifier, blind experiment, statistical study, arbitrary quantitative score, or prescribed tooling. The Project Owner remains the final v0.1 acceptance authority. Phase 2 may define consistent concrete procedures/evidence but may not silently weaken these interpretations; numerical metrics may later supplement them when evidence supports them.

## v0.1 exclusions and non-goal mapping (Item 52)

All Phase 0 v0.1 non-goals remain in force, including no vector/embedding retrieval, knowledge graph/database, autonomous agent framework, GUI/web application, cloud deployment, enterprise-scale/high-availability architecture, unsupported external source integrations, automatic authoritative-document modification, AI governance authority, secret retrieval, enterprise IAM/SSO, large-scale optimization, real-time/event-driven ingestion, multi-user collaborative UI, or universal project/document support.

The approved interpretations are: relationships do not require a graph database/knowledge graph; selection does not require embeddings/vector database; extensibility does not require Slack/Teams/Nevis adapters; authorization does not require enterprise IAM/SSO; rendering does not require a GUI/web app; historical/audit behavior does not require event sourcing, temporal DB, SIEM, or indefinite retention; Candidate/inference concepts do not require agents; interoperability does not require a public API/external standard; and secret retrieval remains excluded. If a non-goal becomes necessary, escalate for Project Owner scope reconsideration rather than silently implementing it. Phase 2 should seek the least sufficient v0.1 architecture.

## Company AI Roadmap proving ground (Item 53)

The first external proving ground uses a fresh Consumer session/execution without development-session knowledge. Context Engine must generate initialization context sufficient to establish Project identity, purpose, governance, current phase/status, authorization, approved/current work, constraints, terminology, unresolved items, and Provenance from a non-circular governed Bootstrap. It must preserve approved/Candidate/historical/conflict/uncertainty distinctions; enable identification of the next legitimate activity without manual reconstruction; demonstrate meaningful continuation (not recall); prohibit unauthorized later phases; test supersession, Candidate handling, isolation, and a missing/unavailable/uncertain scenario; preserve usable provenance for material state Claims; compare with manual reconstruction; use no arbitrary token target; introduce no AI-Roadmap-specific core behavior. Project Owner review may determine acceptance.

## Context Engine dogfooding (Item 54)

Context Engine is a v0.1 Project using the same core mechanisms as external Projects. A fresh Consumer must receive a task-specific package sufficient to continue from governed state without accumulated conversation knowledge. It must use the same Project, Source, Artifact, Claim, Authority, Provenance, selection, Context Item/Package, security, and rendering semantics, with no privileged hard-coded self knowledge. Permitted project configuration must use generally available mechanisms.

The package must correctly communicate purpose, governance, status/authorization, approved/current work, constraints, unresolved items, and provenance; distinguish Phase 1 concepts from Phase 2 implementation decisions, and illustrations from decisions; preserve historical/superseded and Candidate/proposal/open-question distinctions; identify the next legitimate activity without entering Phase 2/implementation. Acceptance tests meaningful continuation and at least one conflict, uncertainty, missing-information, or Source-limitation case. Failures first inform potential general deficiencies, not project-specific hacks. Minimum Sufficient Context applies without recursive inclusion of every package/fact; packages may participate in later provenance without unbounded recursion. Project Owner review may determine acceptance; success evidences generality, not universal applicability.

Specific citations are used where available; broad citations only supplement them. Clarification, supersession, retirement, or replacement preserves historical traceability. Later Phase 2 design, implementation, and evidence should extend—not replace—this mapping. No specialized traceability technology is required.
